# 2026-09-29 RISC-V：box64（BOX32）与 qemu-i386

## 0. 结论

| 转译器 | moresampler（13 个文件） | resampler.exe（11 个文件） | 条件 |
|---|---|---|---|
| box64 0.4.5（BOX32） | 仅 wavtool 一致，其余大量不同 | 全部一致 | 动态链接的加载器，`BOX64_DYNAREC_FASTROUND=0` |
| qemu-i386 11.0.50 | 11 个一致，`bam.wav.llsm` 与 `desc.mrq` 不同 | 全部一致 | 静态链接的加载器 |
| qemu-i386 11.0.50，x87 超越函数以 binary128 计算（补丁） | **全部一致** | **全部一致** | 静态链接的加载器 |
| **qemu-i386 v11.1.2 加同一补丁（采用的方案）** | **全部一致** | **全部一致** | 静态链接的加载器 |

作者决定 RISC-V 采用打补丁的 qemu-i386。补丁与基线见 [`third-party/qemu/`](../../third-party/qemu/README.md)：tag `v11.1.2`，提交 `4fc49f46dc95d4a27de2509e7fceb2931e91faeb`。

差异都已定位到转译器的 x87 模拟（第 5、7 节）。加载器本身在三种转译器下不需要修改语义，box32 只需要动态链接的构建。

## 1. 环境

- 主机：`ssh dp1000`，**riscv64**（Ubuntu 24.04，8 核，GCC 13）。作者说明 box64 在该主机上，实际没有 rover2024 目录（查找到第 5 层）。
- box64：源码 `~/box64-ae-cpp`，0.4.5（`77f2b751`），不是 git 仓库。其 `build/` 未启用 BOX32，不能运行 32 位程序，未改动。
- 本次构建：`~/moreloader-m2/box32-build/box64`，`cmake -DRV64=1 -DBOX32=ON -DCMAKE_BUILD_TYPE=RelWithDebInfo`，在源码树之外。

## 2. 静态链接的加载器不能运行

实测：静态链接的 `moreloader` 连 `--help` 都以 SIGSEGV 结束。box32 的日志：

- `Warning, box64 is not really compatible with staticaly linked binaries. Expect crash!`
- 静态 glibc 启动时调用的 `brk`（45）、`set_tid_address`（258）、`set_robust_list`（311）、`rseq`（386）为 `Unsupported Syscall`。
- 崩溃于 `__libc_start_main + 0x777`。推断：静态 glibc 以辅助向量中的程序头做 IRELATIVE 重定位与 TLS 初始化，box32 自行加载 ELF 而不提供这些信息。未查证，因为下一节的做法绕开了这个问题。

box32 的设计是 x86 程序动态链接 glibc，由 box32 以本机的 libc 代替（日志：`Using native(wrapped) libc.so.6` 等）。因此：

- `MORE_STATIC=OFF` 时仍静态链接 libstdc++ 与 libgcc（`-static-libstdc++ -static-libgcc`），只动态链接 glibc，因为 box32 不提供 C++ 运行库。
- 构建：`MORE_STATIC=OFF`、不构建测试（动态链接的 32 位程序在构建机上缺少 `/lib/ld-linux.so.2`，不能直接运行）。
- box32 要求可执行文件有执行权限，`scp` 复制后须 `chmod +x`，否则报告 `is not an executable file`。

动态链接的加载器在 box32 下：`--help` 正常；不带参数运行 moresampler 的输出与 Windows 相同。FS 段经 32 位的 `set_thread_area` 建立（box32 的 `x86syscall_32.c` 实现了 `set_thread_area` 与 `modify_ldt`）。

## 3. `double free or corruption (out)`

比较中，频率表生成与渲染都以本机 glibc 的 `double free or corruption (out)` 结束，只有 wavtool 模式成功。

排查：

- box32 的包装：`malloc` 为 `calloc(1, size)`，`calloc`、`realloc`、`free` 直接交给本机 glibc（`wrapped32/wrappedlibc_private.h`、`wrappedlibc.c`），彼此一致。
- ASan：加载器以 `-fsanitize=address -static-libasan` 动态链接，用 overlay 的 `ld-linux.so.2` 在 WSL 中运行频率表生成，没有任何报告。加载器自身以及经由包装函数（`memcpy`、`memset` 等）的访问没有越界。
- 客体直接写内存的越界 ASan 查不到。为此增加诊断选项 `--check-heap`（`lib/CRT/GuestHeap.cpp`）：msvcrt 堆的每块有 16 字节头与 16 字节保护区，释放与重新分配时检查，报告块大小、分配处与释放处的客体地址。以故意多写 1 字节的 `memcpy` 确认检查能报告越界。WSL 中频率表生成与渲染都没有报告，客体没有越界。
- `--check-heap` 在 box32 下的结果不同：客体在 `0x4123b0` 从指针数组中取出空指针后访问。这说明客体算出的数组大小或下标与原生不同。
- box64 的 dynarec 默认开启 `BOX64_DYNAREC_FASTROUND`，文档说明该选项生成不精确的 x86 舍入。以 `BOX64_DYNAREC=0`（解释器）或 `BOX64_DYNAREC_FASTROUND=0` 运行，频率表生成正常完成（实测）。

结论：崩溃由 box64 dynarec 的快速舍入造成。GCC 的 `(int)` 转换以 `fldcw` 设为截断后执行 `fistp`，舍入不正确时大小与下标偏差，导致越界与空指针。以 box64 运行时必须设置 `BOX64_DYNAREC_FASTROUND=0`。

## 4. 与 Windows 的比较

`compare.py` 增加 `--loader`，以动态链接的加载器运行：

```
python moreloader/tests/manual/compare/compare.py --host dp1000 --loader build-dynamic/out/bin/moreloader --runner "env BOX64_DYNAREC_FASTROUND=0 BOX64_NOBANNER=1 /home/ubuntu/moreloader-m2/box32-build/box64" [--program resampler]
```

| 程序 | 结果（实测） |
|---|---|
| moresampler | wavtool 的 `mix.wav` 一致；`.llsm`、`desc.mrq`、输出 WAV 大量不同，`baf.wav.llsm` 与 `bam.wav.llsm` 的大小也不同 |
| resampler.exe | 4 个输出 WAV 与 3 个 `.frq` 等 11 个文件全部一致，4 步共 68 秒 |

`BOX64_DYNAREC=0`、`FASTROUND=0`、`FASTROUND=0` 加 `FASTNAN=0` 加 `X87DOUBLE=1` 三种设置下 `ae.wav.llsm` 各不相同，也都不同于 Windows。

## 5. x87 的位级比较

`moreloader/tests/manual/x87/x87probe.c` 在控制字 `0x27F`（Windows）与 `0x37F` 下，对 10 个输入执行 `fsin`、`fcos`、`fptan`、`fsqrt`、`f2xm1`、`fyl2x`、`fpatan`、`frndint`、除以 3、乘以 80 位的 π、截断的 `fistp`，输出 80 位与 double 的位型。在 WSL 原生（处理器）与 box32（解释器与 dynarec 结果相同）下各运行一次（实测，结果在 `work/x87/`）：

- 80 位结果：208 行中 138 行不同。box64 以 double 保存 x87 寄存器。
- double 结果，控制字 `0x27F`：
  - 乘以 80 位的 π：10 个输入中 3 个末位不同。80 位常量先被舍入为 double。`fldpi`、`fldl2e`、`fldln2` 等常量同理（推断）。
  - `f2xm1`（x=0.1）末位不同；`fptan`（x=12345.678）末位不同。
  - `fsqrt(-2.5)` 的 NaN 符号不同：x86 的默认 NaN 为 `0xFFF8…`，box64 为 `0x7FF8…`。
  - 截断的 `fistp`、`frndint`、`fsin`、`fcos`、`fyl2x`、`fpatan`、除法在这些输入上一致。

box64 的选项（`docs/USAGE.md`）：`BOX64_DYNAREC_X87DOUBLE` 默认 0 为「尽可能以 float 模拟 x87」，1 为只用 double，2 为按精度控制降低精度；`BOX64_X87_NO80BITS` 只影响 80 位数的装入与存储。没有以 80 位模拟 x87 运算的选项。

结论：moresampler 的输出差异来自 box64 以 double 模拟 x87，具体为 80 位常量与中间值的舍入、`f2xm1` 与 `fptan` 的末位，以及 NaN 的符号。这些末位差异经 moresampler 的迭代分析与阈值判断翻转了离散判定，因而差异大，属于 CLAUDE.md 所说的「浮点差异翻转了某个离散判定」的情形，差异源已定位到上述指令。哪一个判定被翻转尚未定位。加载器无法在不修改 box64 的情况下使 moresampler 在 box64 上逐字节一致。resampler.exe 用到的 x87 运算不在这些情形之中，因而一致（推断，依据为比较结果）。

## 6. qemu-i386

dp1000 上没有 qemu-i386，以 `~/qemu`（QEMU 11.0.50，不是 git 仓库）在源码树之外构建：`~/moreloader-m2/qemu-build`，`configure --target-list=i386-linux-user --disable-system --disable-docs --disable-tools --disable-werror`。

- 静态链接的加载器直接运行，不需要动态链接的构建：`qemu-i386 ./moreloader <exe> …`。FS 段经 `set_thread_area` 建立，qemu 用户态支持。
- 比较（实测，`--runner /home/ubuntu/moreloader-m2/qemu-build/qemu-i386`）：moresampler 的 13 个文件中 11 个一致，`bam.wav.llsm`（2261 字节，大小相同）与 `desc.mrq` 中 `bam.wav` 的条目（60 字节）不同；resampler 的 11 个文件全部一致。单步约 10 至 90 秒。

## 7. qemu 的 x87 与补丁

x87 探针在 qemu 下（实测，`work/x87/x87-qemu.txt`）：只有 `fsin`、`fcos`、`fptan` 与处理器不同，每条的 10 个输入全部不同，80 位结果的低 11 位为 0；其余指令（`f2xm1`、`fyl2x`、`fpatan`、80 位常量的乘法、除法、NaN 的符号、截断的 `fistp`）在 80 位上逐位相同。double 结果只有 `fptan`（x=12345.678）末位不同。

qemu 的实现（公开资料，`target/i386/tcg/fpu_helper.c`）：`helper_fsin`、`helper_fcos`、`helper_fsincos`、`helper_fptan` 把参数转换为 double，以主机的 `sin`、`cos`、`tan` 计算，再转换回 floatx80。参数与结果都只有 53 位。

moresampler 使用这些指令（静态分析，`work/moresampler.dis`）：`fsin` 2 处、`fcos` 29 处、`fsincos` 24 处；加载器的 `tan` 按 msvcrt 以 `fptan` 实现。结果虽在存入内存时舍入为 double，但寄存器中的值以 64 位尾数参与后续运算，因此精度损失会传播。

补丁（`work/qemu/x87-quad-transcendentals.patch`，应用于源码副本 `~/moreloader-m2/qemu-src`，构建于 `~/moreloader-m2/qemu-x87-build`）：四个函数把 floatx80 无损转换为主机的 binary128 `long double`（riscv64 的 `long double` 为 binary128），以 `sinl`、`cosl`、`tanl` 计算，按 64 位尾数舍入回 floatx80。x87 的精度控制不作用于这些指令（Intel SDM），所以不按控制字舍入。参数范围的检查不变。

结果（实测）：

- x87 探针：与处理器相比，80 位结果只剩 16 处末位不同（`fcos` 4、`fsin` 2、`fptan` 2，两种控制字各一次），与 **FEX 的结果逐位相同**（`work/x87/x87-fex.txt`），double 结果只剩 `fptan`（x=12345.678）。
- 比较：moresampler 13 个文件、resampler 11 个文件全部逐字节一致。

这证实了 qemu 下 `bam.wav` 的差异来自 `fsin`、`fcos`、`fsincos`、`fptan` 的精度。与处理器仍有的末位差异在这批测试数据中不影响输出，这与 FEX 下全部一致的结果相符。

`~/qemu` 没有版本库信息，对应的上游提交未确定。作者决定改以最新的正式版为基线：v11.1.2（`4fc49f46dc95d4a27de2509e7fceb2931e91faeb`）浅克隆于 `~/moreloader-m2/qemu-v11.1.2`，补丁以偏移量应用成功，以 `git diff` 重新生成为 `third-party/qemu/x87-binary128-transcendentals.patch`，构建于 `~/moreloader-m2/qemu-v11.1.2-build/qemu-i386`。结果（实测）：x87 探针与 FEX、与打补丁的 11.0.50 逐位相同；moresampler 13 个文件、resampler 11 个文件全部逐字节一致。

## 8. 66 位 π 的参数约化

第 7 节的补丁以真正的 π 计算，在 sin、cos 的零点附近与处理器差异很大：处理器以舍入到 66 位的 π/2 为模数做参数约化（`20260929-render-comparison.md` 第 7.2 节，由第 60 步的 90 万个操作数得出）。作者同意把该约化加入补丁。

1. **模型**（`moreloader/tests/manual/x87/x87model.c`，x86_64，libquadmath）：以 66 位的 π/2 求最近的整数倍 k，`fmaq` 一次舍入得到约化后的参数，以 binary128 计算 `sin`、`cos`、`tan`（k 为奇数时 `tan` 取 `-cos/sin`），舍入到 80 位。输出即 `x87replay` 的输入，`x87replay` 报告处理器与模型不同的操作数。
2. **操作数**：π/2 的 1 至 399 倍、300 个 2^40 以内的随机倍数、100 个 2^40 至 2^62 的随机倍数，各取最近的 80 位值及其前后 3 个 ulp，正负两号；另有 20000 个指数在 2^-30 至 2^40 之间的随机值。共 31186 个操作数，每个执行 `fsin`、`fcos`、`fptan`，93558 个结果。
3. **与处理器比较**（实测，`work/x87model/`）：AMD Ryzen 7 9700X 上 1052 个结果与模型不同，Intel Core i7-10700 上 2251 个，全部为 ±1 ulp，其中 `fptan` 分别为 755 与 1533 个。没有大于 1 ulp 的差异，`fptan` 同样如此。
4. **补丁**：`x87_reduce` 以 `nearbyintl` 求 k、以 `fmal` 求约化后的参数，`x87_sin`、`x87_cos`、`x87_tan` 按 k 模 4 选取函数与符号，四个 helper 改为调用它们。以 `git diff --abbrev=12` 重新生成 `third-party/qemu/x87-binary128-transcendentals.patch`，构建于 `~/moreloader-m2/qemu-v11.1.2-build/qemu-i386`。
5. **结果**（实测）：
   - 在打补丁的 qemu-i386 下运行 `x87replay`，以模型的结果为参照：93558 个结果逐位相同。
   - x87 探针（208 行）与处理器逐位相同（第 7 节的补丁有 16 处末位不同）。
   - `compare.py`：moresampler 13 个文件、resampler 11 个文件全部逐字节一致。
   - 与处理器仍有的 ±1 ulp 差异来自处理器自身的求值，AMD 与 Intel 之间同样存在，qemu 无法同时与两者一致。
